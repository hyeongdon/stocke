# 다중 증권계좌 및 연금저축 ETF 모으기 개발계획

## 1. 문서 목적

현재 키움증권 중심으로 구성된 Stocke에 KB증권 연금저축 계좌와 다른 주식계좌를 추가해, 계좌별 자산을 구분하고 ETF 적립 계획을 관리하기 위한 개발 범위와 진행 순서를 정리한다.

이 문서는 개발 계획이며 특정 ETF의 매수나 투자 성과를 권유하지 않는다. 실제 주문은 사용자가 명시적으로 활성화하고 최종 확인한 경우에만 수행한다.

## 2. 현재 상태와 주요 제약

- 애플리케이션은 FastAPI, SQLAlchemy, SQLite/PostgreSQL 구성이다. 시작점과 기존 기능은 [모듈 처리 개요](./MODULE_PROCESS_OVERVIEW.md), [아키텍처 문서](./ARCHITECTURE_DIAGRAM.md)를 참고한다.
- 증권사 API 호출은 `api/kiwoom_api.py`와 관련 모듈에 있으며, 계좌번호와 모의/실전 구분은 현재 `core/config.py`의 키움 전역 환경설정에 의존한다.
- `positions`에는 키움 모의/실전 구분(`account_mode`)이 있지만, 임의의 증권사·복수 계좌를 식별하는 계좌 외래키 구조는 없다. 신호, 주문 실행기, 잔고 동기화도 키움 계좌 가정이 있으므로 계좌 식별자를 UI에만 추가해서는 충분하지 않다.
- KB증권 계좌를 키움 API로 조회·주문할 수 있다고 가정하지 않는다. KB증권의 공식 API/제휴 연동 가능 여부, 연금저축 계좌 지원 범위와 주문 제약을 먼저 확인해야 한다. 확인되지 않으면 해당 계좌는 조회 전용 또는 수동 입력 방식으로 시작한다.

### 2.1 0단계 진행 결과 (2026-11-01)

**내부 코드 기준 조사 완료, 외부 연동 및 사용자 정책 확인 대기** 상태다.

| 확인 항목 | 현재 확인 결과 | 계획에 미치는 영향 |
|---|---|---|
| 증권사 연동 구조 | 코드에서 키움 API 외의 브로커 어댑터 구현은 확인되지 않았다. | 새 증권사는 어댑터와 capability를 추가해야 하며, 키움 기능을 그대로 쓸 수 있다고 가정하지 않는다. |
| 계좌 설정 | `core/config.py`에서 키움 계좌번호 및 모의/실전 모드를 전역 설정으로 선택한다. | 복수 계좌는 환경변수만 늘리는 방식이 아니라 계좌별 설정/식별 모델이 필요하다. |
| 보유 포지션·주문 | `positions`에는 `account_mode`가 있으나 일반 `account_id`가 없다. `sell_orders`는 포지션 ID를 참조하고, 주문 실행 경로는 키움 API를 직접 사용한다. | 포지션·주문·체결·신호의 계좌 귀속을 함께 설계해야 한다. |
| 잔고 스냅샷 | `account_balance_snapshots`는 키움 계좌용이며 날짜당 한 건을 전제로 한다. | 계좌 ID 및 데이터 출처를 포함하도록 확장할 필요가 있다. |
| KB증권 연동 | 공식 API/제휴 여부와 연금저축 계좌의 조회·주문 기능은 아직 검증되지 않았다. | 공식 문서 또는 계정별 안내로 확인 전까지 `KBAdapter`의 주문 지원을 확정하지 않는다. |
| 추가 계좌 및 적립 정책 | 추가 계좌의 증권사와 자동주문·주기·금액 등은 아직 미확정이다. | 아래 10절의 의사결정 항목이 정해져야 범위와 연동 조사 대상을 확정할 수 있다. |

**0단계 종료 조건:** 공식 연동 근거와 계좌별 지원 기능을 확인하고, 추가 계좌 및 적립 정책을 확정한다. 현재는 내부 구조 조사까지만 완료되어 0단계 전체를 완료 처리하지 않는다. 공식 API 지원을 확인할 수 없으면 KB 연금저축은 조회 전용 또는 수동 기록으로 한정하고, 주문 연동을 후속 범위로 보류한다.

## 3. 목표와 범위

### 목표

1. 증권사와 계좌 종류가 다른 계좌를 하나의 화면에서 구분해 관리한다.
2. 연금저축 계좌의 ETF 적립 계획과 실행 예정 내역을 관리한다.
3. 각 계좌의 잔고·보유종목·주문·체결 정보를 출처와 갱신 시각을 포함해 표시한다.
4. 기존 키움 자동매매가 계좌 분리로 인해 다른 계좌에 주문하지 않도록 안전하게 격리한다.

### 1차 범위

- 계좌 등록/수정/비활성화, 별칭, 증권사, 계좌 유형, 조회/주문 가능 상태 표시
- 계좌별 잔고 및 보유종목 조회 또는 수동 스냅샷 입력
- ETF 적립 계획 설정(종목, 주기, 금액/수량, 실행일, 활성 상태)
- 실행 예정 및 실행 결과 기록, 미체결/실패 상태 표시
- 다중 계좌를 반영한 DB·API·UI 구조
- 주문 실행 전 계좌/증권사/계좌 유형/주문 가능 상태 검증

### 1차 제외

- 종목 추천, 수익률 보장, 세금 최적화 자문
- 기존 키움 자동매매 전략을 모든 증권사 계좌로 확대
- 증권사 인증 우회, 화면 스크래핑 또는 비공식 주문
- 자동 환전, 해외주식 주문, ETF 소수점 주문(각 API의 공식 지원 확인 전)
- 증권사 계좌 비밀번호나 API 비밀키를 평문으로 DB 저장

## 4. 권장 설계

### 4.1 계좌와 연동 어댑터 분리

계좌 정보와 증권사 API 연동을 분리한다. 비즈니스 로직이 특정 증권사 SDK나 HTTP 형식에 직접 의존하지 않도록 공통 인터페이스를 둔다.

```text
화면/API
  └─ 계좌·적립 서비스
       ├─ 계좌 저장소
       ├─ 브로커 어댑터 인터페이스
       │    ├─ KiwoomAdapter (기존 API를 점진적으로 감싸기)
       │    ├─ KBAdapter (공식 지원 범위 확인 후 구현)
       │    └─ ManualAdapter (수동 스냅샷/실행 기록)
       └─ 적립 스케줄러 → 주문 초안/주문 실행 → 체결 대사
```

어댑터의 최소 기능은 지원 기능 조회, 연결 상태 확인, 잔고/보유 조회, 주문 가능 수량·금액 확인, 주문 제출, 주문 상태/체결 조회로 한다. 지원되지 않는 기능은 성공처럼 보이게 처리하지 않고 `미지원` 상태와 사유를 응답한다.

### 4.2 데이터 모델 초안

기존 모델을 한 번에 교체하지 않고, 계좌 식별을 추가한 뒤 각 사용 경로를 단계적으로 이전한다.

| 테이블/개념 | 주요 필드 | 목적 |
|---|---|---|
| `broker_accounts` | `id`, `broker`, `account_type`, `alias`, `account_no_masked`, `environment`, `status`, `capabilities`, `created_at`, `updated_at` | 증권사별 계좌 메타데이터. 계좌번호는 필요 최소한으로 저장하고 화면/로그에서는 마스킹 |
| `etf_saving_plans` | `id`, `account_id`, `symbol`, `name`, `frequency`, `scheduled_day`, `amount_krw` 또는 `quantity`, `order_policy`, `enabled`, `next_run_at` | 연금저축 ETF 적립 규칙 |
| `investment_runs` | `id`, `plan_id`, `scheduled_at`, `status`, `requested_amount`, `order_id`, `message`, `created_at` | 예정 실행과 결과 이력, 중복 실행 방지 |
| `broker_orders` (또는 기존 주문 모델 확장) | `account_id`, `broker_order_id`, `client_order_key`, `symbol`, `side`, `quantity`, `price`, `status`, 체결 수량/금액 | 계좌별 주문·체결 대사 |
| `account_balance_snapshots` 확장 | `account_id`, `source`, `as_of`, 잔고/평가 정보 | 계좌별 시점 잔고와 데이터 출처 기록 |

`account_mode`는 기존 키움 모의/실전 구분을 위해 당분간 보존하고, `account_id`를 새 기준으로 추가한다. 마이그레이션 시 기존 포지션·신호·주문은 현재 설정으로부터 기존 키움 계좌와 연결한다. 연결이 불가능한 과거 데이터는 임의 계좌에 배정하지 않고 검토 대상으로 남긴다.

### 4.3 적립 실행 안전장치

- 스케줄러는 주문을 곧바로 실행하지 않고, 먼저 실행 건과 주문 초안을 생성한다.
- MVP 기본값은 `자동주문 OFF`; 사용자가 계좌와 적립 규칙을 확인하고 활성화해야 주문이 가능하다.
- 매 실행 시 계좌 활성/주문 가능 여부, 어댑터 기능 지원, 거래일/주문 시간, 잔고·한도, ETF 주문 가능 여부를 재검증한다.
- `plan_id + scheduled_at`에 고유 제약 또는 동등한 원자성 보장을 적용해 재시작·재시도에도 중복 주문을 막는다.
- 주문 접수 응답만으로 체결 완료로 표시하지 않는다. 주문 상태 조회/잔고 대사 전까지 접수·미체결·확인 중 상태를 유지한다.
- API 실패, 시간 초과, 결과 불명 상태는 무조건 재주문하지 않는다. 주문 조회로 접수 여부를 확인한 후 재시도 가능 여부를 결정하고, 확인 불가 시 수동 확인 대상으로 표시한다.
- 정액 매수에서 1주 가격이 예산을 넘거나 소수점 주문이 지원되지 않는 경우의 잔액 이월/미집행 정책은 사용자 결정 전에는 자동 처리하지 않는다.

## 5. 개발 단계 및 완료 기준

### 0단계 — 연동·업무 조건 확인 (진행 중)

- KB증권의 공식 API 또는 공식 제휴 채널 유무, 연금저축 계좌의 잔고/주문/체결 지원 범위를 확인한다.
- 주문 인증/토큰 발급, 운영 및 테스트 환경, 호출 제한, ETF 주문 가능 조건, 자동주문 허용 여부를 확인한다.
- “다른 주식계좌”의 증권사와 계좌 유형을 확정한다.
- 적립 규칙(정액/수량, 주기, 휴일 처리, 매수 가격 방식, 잔액 처리, 자동주문 승인 방식을 확정한다.
- 내부 코드 조사 결과는 2.1절과 같다. 공식 API 문서 또는 KB증권의 계좌별 안내를 확인하기 전까지 연동 가능 여부를 미확정으로 둔다.
- **완료 기준:** 계좌별 `API 연동`, `조회 전용`, `수동 기록` 중 가능한 운영 모드를 근거와 함께 결정한다. 공식 주문 인터페이스가 확인되지 않으면 자동주문 단계로 넘어가지 않는다.

### 1단계 — 다중 계좌 기반과 데이터 마이그레이션

- `broker_accounts`와 계좌 저장소/서비스를 추가한다.
- 계좌 식별자를 포지션, 잔고 스냅샷, 주문, 적립 실행에 연결한다.
- 기존 키움 설정을 기존 계좌 레코드로 초기 등록하는 마이그레이션 및 롤백/백업 절차를 만든다.
- 기존 키움 API를 어댑터 뒤로 감싸되, 기존 단일 계좌 동작을 유지한다.
- **완료 기준:** 기존 계좌 데이터가 보존되고 기존 키움 주문·잔고 화면의 회귀 테스트가 통과한다. 두 계좌의 같은 종목 보유가 서로 합쳐지지 않는다.

### 2단계 — 계좌 관리 및 조회 화면

- 계좌 목록, 상세, 연결 상태, 마지막 갱신 시각, 데이터 출처를 제공한다.
- 읽기 전용/주문 가능/연동 미지원 상태를 명확히 표시한다.
- 공식 연동이 없는 계좌에는 CSV 업로드 또는 수동 스냅샷 입력을 제공할지 구현 범위를 확정한다.
- 계좌번호 및 인증정보가 로그/API 응답에 노출되지 않도록 마스킹하고, 권한 없는 계좌 설정 변경을 차단한다.
- **완료 기준:** 복수 계좌의 총액과 계좌별 자산이 구분되고, 오래되었거나 수동 입력인 데이터가 실시간 데이터처럼 표시되지 않는다.

### 3단계 — ETF 적립 계획 및 시뮬레이션

- 적립 계획 CRUD, 실행 예정 달력/목록, 예상 주문 초안 및 실행 이력을 제공한다.
- 거래일 달력 기준 휴일 처리, 중복 실행 방지, 계획 일시중지/재개를 구현한다.
- 처음에는 주문을 전송하지 않는 미리보기/드라이런으로 한 주기 이상 검증한다.
- **완료 기준:** 예약 실행 시각, 대상 계좌·ETF, 예산/수량, 주문 초안이 재현 가능하고 실패/재시작 시 중복 실행이 없다.

### 4단계 — 공식 주문 연동 및 제한적 운영

- 공식 지원이 확인된 브로커 어댑터에 한해 주문 제출/조회/체결 대사를 구현한다.
- 자동주문은 기본 비활성화로 제공하며, 계좌 단위의 별도 명시적 활성화 및 최대 집행 금액 제한을 둔다.
- 모의/테스트 환경이 있으면 그 환경에서 먼저 검증하고, 소액 실계좌는 별도 승인 후 점진적으로 시작한다.
- **완료 기준:** 접수·미체결·부분체결·체결·거절·결과 불명 상태를 구분하고, 주문 재시작·네트워크 오류·중복 스케줄 테스트를 통과한다.

### 5단계 — 운영 안정화

- 적립 실행 결과와 오류 알림, 수동 확인 큐, 계좌 잔고/체결 대사 화면을 제공한다.
- 계좌별 API 제한 및 재시도 정책을 검증하고, 실패/지연/중복 방지 지표를 기록한다.
- 백업, 마이그레이션 복구, 인증정보 교체 절차를 운영 문서에 추가한다.
- **완료 기준:** 사용자가 각 실행의 예정·주문·체결·실패 상태를 추적할 수 있고, 미확인 주문을 자동으로 중복 제출하지 않는다.

## 6. API 및 화면 초안

기존 라우트/네이밍에 맞춰 확정하되, 다음 리소스 경계를 권장한다.

```text
GET    /accounts
POST   /accounts
GET    /accounts/{account_id}
PATCH  /accounts/{account_id}
POST   /accounts/{account_id}/refresh

GET    /etf-savings
POST   /etf-savings
PATCH  /etf-savings/{plan_id}
POST   /etf-savings/{plan_id}/preview
POST   /etf-savings/{plan_id}/enable
POST   /etf-savings/{plan_id}/pause
GET    /etf-savings/{plan_id}/runs
```

계좌 관리 화면에는 증권사/별칭/계좌 유형/연금저축 여부/연결 상태/마지막 갱신 시각을, 적립 화면에는 ETF/계좌/주기/예산/다음 실행일/자동주문 상태/최근 실행 결과를 표시한다. 계좌와 계획을 삭제하기보다 비활성화해 주문 및 감사 이력을 보존한다.

## 7. 보안·운영 요구사항

- API 키/시크릿/비밀번호는 기존 비밀정보 관리 방식을 따르고 소스, DB 일반 컬럼, 응답 본문, 로그에 기록하지 않는다. 필요한 경우 암호화된 비밀정보 저장소를 별도 검토한다.
- 계좌번호는 표시 시 마스킹하고, 로그와 감사 이력에는 계좌 내부 ID를 사용한다.
- 주문 기능은 계좌별 capability 및 활성화 상태를 매번 확인한다. 조회용으로 등록된 계좌에서 주문 API가 호출되면 서버에서 거부한다.
- 주문 요청은 사용자/계좌/계획/요청 키/주문 결과를 감사 가능하게 기록하되 인증정보는 제외한다.
- API 응답의 오류·미지원·오래된 데이터 상태를 명시한다. 빈 보유내역을 정상 잔고로 간주하지 않는다.
- 주문 연동은 실제 계좌에 영향을 주므로, 자동주문 활성화와 큰 금액/대량 변경에는 추가 확인 절차를 둔다.

## 8. 테스트 계획

- **단위:** 어댑터 공통 응답, 계좌 capability, 계획 주기·거래일 계산, 예산→수량 산출, 상태 전이, 멱등성 키
- **DB/마이그레이션:** 기존 키움 데이터 이관, 중복/부분 데이터, 마이그레이션 실패 후 복구
- **통합:** 증권사 API 호출은 모의 응답으로 테스트하며, 네트워크 오류/타임아웃/토큰 만료/레이트리밋/결과 불명 응답을 포함
- **회귀:** 기존 키움 단일 계좌의 잔고, 포지션, 주문, 모의·실전 분리
- **안전성:** 계좌 A의 신호·주문이 계좌 B로 전달되지 않음, 비활성 계좌 주문 차단, 재시작/스케줄 중복 방지, 미체결 주문 재주문 차단
- **수동 검증:** 공식 테스트 계좌 또는 드라이런에서 하루 실행→주문 조회→체결 대사 전체 흐름 확인. 실제 주문은 별도 승인 없이 테스트하지 않음

## 9. 주요 위험과 대응

| 위험 | 대응 |
|---|---|
| KB증권 연금저축에 사용할 수 있는 공식 API가 없거나 주문 기능이 제한됨 | 0단계에서 검증. 조회 전용/수동 기록으로 범위를 축소하고 비공식 자동화를 하지 않음 |
| 기존 키움 경로가 전역 계좌 설정에 묶여 있음 | 기능별 점진 이관, 기존 키움 어댑터를 기본값으로 유지, 회귀 테스트 우선 |
| 다중 계좌 전환 중 포지션/주문이 다른 계좌에 연결됨 | 모든 실행 경로에서 `account_id` 필수화, 불명확한 과거 데이터는 자동 추정하지 않음 |
| 반복 스케줄 또는 타임아웃으로 주문 중복 | 실행 고유키, 주문 조회 우선, 결과 불명 시 자동 재주문 금지 |
| 정액 적립 금액으로 ETF 1주를 살 수 없거나 소수점 주문 미지원 | 매수 단위/잔액 처리 정책을 사용자 확인 대상으로 둠 |
| 계좌/인증정보 노출 | 마스킹, 비밀정보 분리, 로그 필터 및 응답 스키마 테스트 |

## 10. 초기 의사결정 항목

구현 시작 전 아래 항목을 확정한다.

1. “다른 주식계좌”의 증권사와 계좌 유형
2. KB 연금저축은 잔고 조회만 필요한지, ETF 주문까지 자동화할지
3. 자동주문 전 단계에서 수동 주문 기록/CSV 가져오기가 필요한지
4. 적립 방식: 매월 정액 또는 주기별 수량, 실행일, 휴일 이월 규칙
5. 1주 미만 잔액의 이월/미집행 방식과 주문 가격 정책
6. 계좌 등록 시 인증정보를 앱에서 직접 보관할지, 운영 환경의 환경변수/비밀정보 저장소로 관리할지

## 11. 예상 일정

외부 API 신청/승인 소요를 제외한 대략적인 범위다.

| 단계 | 예상 기간 |
|---|---:|
| 연동·업무 조건 확인 | 2~5일 (증권사 확인 대기 제외) |
| 계좌 기반·마이그레이션 | 4~7일 |
| 계좌 관리·조회 | 3~5일 |
| 적립 계획·드라이런 | 4~6일 |
| 공식 주문 연동·안전성 검증 | 5~10일 이상 |

2026-11-01 기준 0단계는 내부 코드 조사를 마쳤으나, KB증권 공식 연동 범위와 사용자 업무 조건이 미확정이다. 따라서 이 확인이 끝나기 전에는 후속 구현 단계 착수를 확정하지 않는다. API 지원 여부가 확정되지 않은 상태에서는 실제 주문 단계를 별도 승인/일정으로 분리한다.
